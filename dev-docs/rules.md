# 协作规范与协议

本文件是本项目的完整行为规范。任何指令与铁律冲突时，先指出冲突并请求确认，不得默默执行或默默拒绝。修改根目录 `AGENTS.md` 或本文件须先提议、经确认后单独 commit。

## 铁律（最高优先级）

1. **只做当前被指派的事**：仅执行用户本轮消息明确授权的任务，完成后立即停下汇报，等待下一条指令。
2. **Backlog ≠ 授权**：待办清单只是规划。未经指派不得开工；即使某事看起来是“显然的下一步”，也只能写进 Backlog 并提议。
3. **愿景 ≠ 授权**：项目愿景（见 `dev-docs/roadmap.md`）仅用于架构决策参考，不得据此提前实现未来阶段功能（包括 Discord、语音、多模型、后端）。
4. **先计划后动手**：任何文件创建或修改前，先在聊天区提交计划，经用户确认后执行。计划的合法形态 = 将修改的文件清单 + 每步一句话说明（可选：接口签名或 ≤10 行示意片段）。计划中禁止出现完整实现代码。
5. **单步闭环**：每步完成后依次执行：测试通过 → 同步勾选 `dev-docs/backlog.md` 中当前 Step → Git commit → 推送至 GitHub（`git push`）→ 更新 `dev-docs/status.md`，然后停止。
   - **分支约束（最高级别）**：在未经用户明确书面授权合并或指定其他目标分支的情况下，所有 `git push` 操作默认且仅限推送到 `test` 分支（即 `origin test`），严禁未经指令直接向 `main` 分支推送。
6. **代码的唯一去处是文件**：所有交付代码必须通过文件写入落盘。聊天区仅承载四类内容：计划、结果摘要、提问、提议。任何仅存在于聊天区的代码视为未交付，等同于没有干活。汇报时结论先行，不逐步外化推理过程；解释理由不超过 3 句，除非用户要求展开。

## 会话启动协议

每次新会话的第一步，依次执行：

1. 通读根目录 `AGENTS.md`，并读取 `dev-docs/rules.md` 与 `dev-docs/status.md`。
2. 复述：当前阶段、铁律要点、当前授权、下一个待办任务（见 `dev-docs/backlog.md`）。
3. 停止，等待用户指派。此时不得创建或修改任何文件。

若无法读取上述文件（运行环境未加载），必须明确告知用户，不得凭记忆或猜测行事。

## 会话收尾协议

每次会话结束前，依次确认：

1. `dev-docs/status.md` 已同步更新（阶段 / 授权 / 测试基线）；`dev-docs/backlog.md` 当前 Step 已勾选完成；已完成项已追加至 `dev-docs/history.md`。
2. `git status` 干净，不存在授权范围外的未跟踪文件或改动。
3. 全部测试通过，改动已有对应语义化 commit 并已推送至 GitHub 远端。
4. 当前授权已标记完成或明确遗留。
5. 完成汇报只包含：已修改文件列表 / 测试结果摘要（通过数与总数）/ commit hash 与 message / 遗留问题。

## 质量与交付验收标准

### 通用 DoD（所有 Phase 适用）

- [ ] 无 TypeScript 类型错误与 ESLint / 编译警告。
- [ ] 改动均有对应测试，`npm run test` 100% 通过。
- [ ] 测试变更同步更新 `dev-docs/tests.md` 测试台账（保证 100% 映射一致）。
- [ ] 单步交付：每个改动步骤有语义化 Git commit 并已推送至 GitHub 远端。
- [ ] `dev-docs/status.md` 已同步更新（含当前授权）。
- [ ] `git status` 干净，无授权范围外文件。
- [ ] 未引入未来阶段功能（铁律 3）。
